# 爬取性能优化实施方案

> 项目：ACG 黄油资源聚合爬取工具  
> 日期：2026-09-08  
> 状态：实施前方案  
> 默认策略：平衡模式

## 一、优化目标

在不明显增加限流、漏抓、图片失败和 SQLite 写入冲突的前提下，提高多站点爬取的整体吞吐量。

本次优化不采用单纯降低请求间隔的方式，而采用以下组合方案：

1. 保留四个站点并行爬取。
2. 增加站点内部受控的详情页并发。
3. 将图片下载从详情解析流程中拆出，交给独立后台队列。
4. 根据 403、429、5xx、超时和验证页动态退避。
5. 增加 SQLite WAL、写入重试和统一写入协调。
6. 提供稳定、平衡、快速三个速度档位。
7. 增加每站响应时间、成功率、失败率和处理速度统计。

## 二、当前瓶颈

当前已经通过线程池并行运行四个站点，但每个站点内部仍基本按照帖子逐条解析。详情解析完成前还会立即下载该帖的多张图片，因此核心数据抓取容易被图片服务器、代理或单张图片超时阻塞。

当前主要问题包括：

- `crawler.max_workers` 主要控制站点层线程数，四个站点最多只会实际使用四个站点任务线程。
- 每个站点的详情页解析基本串行。
- 每篇帖子解析过程中立即调用 `download_images()`。
- `download_images()` 每篇帖子最多创建六个图片下载线程，未来若直接增加详情并发，图片请求会被成倍放大。
- 多个站点线程可能同时写入 SQLite，缺少明确的写入退避与协调机制。
- 请求失败虽有重试，但缺少按站点统计、连续失败熔断和动态降速。
- 前端没有速度档位选择，也无法直接观察各站点实时吞吐与失败情况。

## 三、目标并发模型

### 3.1 第一级：站点并发

继续保留站点级线程池，最多同时运行四个启用站点。

每个站点应保持独立状态，包括：

- 当前并发数
- 当前请求间隔
- 连续失败次数
- 成功和失败请求数
- 平均响应时间
- 403、429、5xx 和超时次数
- 是否处于降速或暂停状态

单个站点异常不应导致其他站点停止。

### 3.2 第二级：站内详情并发

默认平衡模式下，各站详情并发建议为：

- ACG 游戏姬：3
- 萌幻 ACG：2
- ACG 图书馆：2
- ACG 俱乐部：2

全部站点同时运行时，最多约九篇详情并行解析。该数量可显著提高吞吐量，同时避免瞬间产生过多页面请求。

站内并发必须是有界线程池，不允许按帖子数量无限创建线程。

### 3.3 共享会话与线程安全

站内详情并发后，需要检查 `requests.Session` 的使用方式。建议每个工作线程使用线程本地 Session，或由站点爬虫为每个详情任务创建可复用但互不共享状态的 Session。

萌幻 ACG 的登录状态需要安全复制到详情工作线程，避免多个线程同时修改同一个登录 Session 的 Cookie。

## 四、图片后台队列

### 4.1 拆分原则

详情页解析只负责提取：

- 标题
- 日期
- 点赞数
- 平台
- 百度网盘链接及提取码
- 移动云盘链接及提取码
- 解压码和作弊码
- 原始图片 URL

只要帖子存在有效下载链接，即可先写入数据库。图片下载不再阻塞核心帖子入库。

### 4.2 图片任务流程

建议流程如下：

1. 详情解析得到原始图片 URL。
2. 帖子携带原始图片地址先写入数据库。
3. 将帖子 ID、来源、原始图片 URL、代理信息放入全局图片队列。
4. 图片工作线程从队列中下载图片。
5. 下载成功后更新帖子 `images` 字段。
6. 下载失败时保留远程原图地址，允许后续重新下载。

### 4.3 图片并发限制

图片下载使用全局固定线程池，而不是每篇帖子单独创建线程池。

建议配置：

- 稳定模式：全局图片并发 2
- 平衡模式：全局图片并发 6
- 快速模式：全局图片并发 10

图片任务应支持去重，同一帖子和同一 URL 不应重复进入队列。

### 4.4 任务完成口径

核心爬取完成与图片下载完成应分开统计：

- 核心数据完成：所有列表和详情任务完成，符合条件的帖子已经入库。
- 图片同步完成：图片队列已经清空，所有可下载图片已处理。

前端可以显示“核心数据已完成，图片后台处理中”，避免用户误以为任务卡住。

## 五、速度档位

### 5.1 稳定模式

适合首次验证选择器、目标站异常、代理不稳定或连续漏抓时。

- 每站详情并发：1
- 请求间隔：0.5 至 1.0 秒
- 全局图片并发：2
- 失败退避：积极
- 连续失败阈值：较低

### 5.2 平衡模式

作为默认模式。

- ACG 游戏姬详情并发：3
- 其他站点详情并发：2
- 请求间隔：0.2 至 0.5 秒
- 全局图片并发：6
- 遇到 403、429、5xx、超时或验证页自动降速

### 5.3 快速模式

仅建议用于较少页数和短时间任务。

- 每站详情并发：4
- 请求间隔：0.1 至 0.3 秒
- 全局图片并发：10
- 连续异常后强制回落到平衡模式

快速模式不能关闭失败保护，也不能突破全局硬并发上限。

## 六、失败保护与动态降速

### 6.1 指数退避

以下情况应进入退避：

- HTTP 403
- HTTP 429
- HTTP 500、502、503、504
- 连接超时或读取超时
- 返回验证页、登录页或明显空白页面

基础退避建议采用指数增长并加入随机抖动，避免多个线程同时重试。

### 6.2 连续失败熔断

每个站点独立统计连续失败次数。

建议策略：

- 连续 3 次失败：并发减少 1，并提高请求间隔。
- 连续 5 次失败：暂停该站一段时间。
- 暂停后恢复时：先以单详情并发试探。
- 再次连续失败：停止该站本轮任务，并记录明确原因。

### 6.3 验证页检测

不能只依赖 HTTP 状态码。部分网站会返回状态码 200 的验证页面。

建议检查：

- 页面标题是否包含验证、访问受限或登录提示。
- 正文长度是否异常过短。
- 详情页关键选择器是否全部缺失。
- 页面是否包含 Cloudflare、captcha、verify、forbidden 等特征。

检测到验证页时不得把内容当作正常帖子写入数据库。

## 七、SQLite 并发保护

### 7.1 WAL 模式

数据库初始化时启用：

- `PRAGMA journal_mode=WAL`
- 合理的 `busy_timeout`
- 连接用完立即关闭

### 7.2 写入重试

遇到 `database is locked` 时采用短暂退避后重试，重试次数耗尽才记录为真正写入失败。

### 7.3 写入协调

优先采用统一数据库写入锁，确保单次帖子插入、图片字段更新、任务统计更新不会互相覆盖。

如果后续写入压力仍明显，可升级为独立数据库写入队列。第一阶段暂不引入额外复杂度。

### 7.4 幂等与去重

在详情请求前检查已存在且字段完整的帖子，避免重复请求。

数据库侧继续依靠来源和来源 ID 的唯一性保证幂等。图片更新不得覆盖已经成功下载的本地路径。

## 八、配置设计

建议在 `config.yaml` 中增加：

- 默认速度档位
- 三种速度档位的延迟和图片并发参数
- 各站详情并发覆盖值
- 全局详情并发硬上限
- 图片队列容量
- 退避配置
- 连续失败暂停阈值
- SQLite busy timeout 和写入重试参数
- 验证页检测开关

现有 `crawler.max_workers` 应重命名或明确标注为站点并发，避免误解为详情线程数。

配置载入时必须设置安全默认值，并限制用户填写的最大并发，防止配置错误导致大量请求。

## 九、前端调整

爬取控制面板增加速度档位：

- 稳定
- 平衡，默认
- 快速

爬取请求将所选档位传给后端，由后端进行白名单校验。

进度区域建议增加：

- 当前速度档位
- 每站已处理数量
- 每站成功、跳过和错误数量
- 每站平均响应时间
- 每分钟处理详情数
- 图片队列待处理数量
- 图片成功和失败数量
- 站点降速、暂停或熔断状态

前端显示仅用于观察，最终统计应以后端状态为准。

## 十、代码改造范围

预计涉及以下文件：

### `acg_crawler/config.yaml`

增加速度档位、站内并发、图片队列、退避和数据库参数。

### `acg_crawler/config.py`

补充配置默认值、兼容旧配置并限制非法并发值。

### `acg_crawler/crawler/base.py`

实现线程安全请求、每站限速、状态码退避、验证页检测、响应时间统计和站点熔断。

### `acg_crawler/crawler/__init__.py`

重构三种爬取模式，增加站点内部详情线程池、统一进度更新和取消处理。

### 四个站点爬虫文件

移除详情解析中的同步图片下载，只保留原始图片地址和核心字段解析。

### `acg_crawler/parser/image_handler.py`

改造为全局有界图片队列和固定工作线程池，增加任务去重、结果回写、停止和排空能力。

### `acg_crawler/database/__init__.py`

启用 WAL、busy timeout、写入锁和锁冲突重试，增加图片字段安全更新函数。

### `acg_crawler/app.py`

接收速度档位，扩展进度接口，管理图片队列生命周期，并修复异常结束后残留 `running` 任务的问题。

### `acg_crawler/templates/index.html`

增加速度档位选择与站点状态展示区域。

### `acg_crawler/static/app.js`

提交速度档位，渲染新进度指标和图片队列状态。

### `acg_crawler/static/style.css`

补充速度选择器、站点状态卡和降速提示样式。

### 项目文档

实施完成后同步更新 README、项目架构交接文档和技术方案交接文档。

## 十一、实施顺序

### 第一阶段：稳定性基础

1. 启用 SQLite WAL、busy timeout 和写入重试。
2. 完善请求异常分类、指数退避与验证页检测。
3. 增加线程安全的统计和取消机制。
4. 修复异常任务残留 `running` 状态。

### 第二阶段：图片解耦

1. 四个站点详情解析不再同步下载图片。
2. 建立全局图片队列和固定线程池。
3. 帖子先入库，图片完成后更新字段。
4. 增加图片队列进度和重新下载兼容处理。

### 第三阶段：站内详情并发

1. 重构按页爬取。
2. 重构按日期爬取。
3. 重构增量爬取。
4. 为各站配置独立详情并发。
5. 确保停止按钮可以尽快终止未开始任务。

### 第四阶段：速度档位与前端

1. 增加稳定、平衡、快速三个档位。
2. 后端按档位生成运行参数。
3. 前端显示每站状态和图片队列状态。
4. 快速模式异常时自动回落。

### 第五阶段：测试与调参

使用三个档位分别进行真实爬取，记录吞吐、失败率、数据完整性和图片完成率，再确定最终参数。

## 十二、测试计划

### 12.1 静态检查

- Python 文件语法检查通过。
- 配置文件可正常载入。
- 前端 JavaScript 无语法错误。
- 旧配置缺少新字段时仍可启动。

### 12.2 单站小规模测试

每个站点分别抓取一页，验证：

- 帖子数量与改造前基本一致。
- 标题、日期、平台、点赞和网盘链接未退化。
- 无网盘帖子仍被过滤。
- 图片下载失败不会阻塞帖子入库。
- 验证页不会被当作正常帖子。

### 12.3 多站并发测试

四站同时各抓取一至三页，验证：

- 所有站点可以并行工作。
- 站内详情并发符合配置。
- 没有 `database is locked` 未处理错误。
- 成功、跳过、错误统计与实际入库数量一致。
- 停止任务后不会继续大量请求。

### 12.4 三轮真实测试

第一轮使用稳定模式，验证数据正确性。

第二轮使用平衡模式，与稳定模式对比总时长、失败率和完整性。

第三轮使用快速模式，观察 403、429、超时、空页面和自动降速行为。

### 12.5 回归测试

必须验证：

- 历史记录正常。
- 按批次导出正常。
- PC 与 PC+安卓分类正常。
- 本地图片和远程图片均可展示。
- 重新下载图片功能正常。
- 导出 ZIP 中的图片路径正常。
- 双网盘置顶和点赞排序规则未改变。

## 十三、验收标准

达到以下条件才视为完成：

1. 默认平衡模式下，四站真实爬取总耗时相比当前串行详情模式有明显下降。
2. 平衡模式的数据入库数量与稳定模式相比没有明显异常减少。
3. 没有未处理的 SQLite 锁错误。
4. 图片下载失败不会阻塞核心帖子入库。
5. 403、429、5xx、超时和验证页能够触发退避或降速。
6. 单站连续失败不会拖垮其他站点。
7. 停止按钮可终止新任务提交并正确结束任务状态。
8. 三种速度档位均可从前端选择并由后端安全执行。
9. 原有爬取、展示、历史、删除、重新下载图片和导出功能通过回归测试。
10. README 和交接文档已同步更新。

## 十四、回滚方案

实施前保留当前代码状态和配置备份。改造按照阶段拆分，每个阶段完成后单独检查和提交。

如果站内详情并发导致解析不稳定，可以通过配置将各站详情并发恢复为 1，不需要回退全部代码。

如果图片后台队列出现问题，可以暂时关闭自动图片下载，保留原始图片 URL，并继续使用现有“重新下载图片”功能补图。

如果动态限速判断不稳定，可以关闭动态调节，保留固定档位参数与基础重试。

## 十五、默认实施结论

本次按以下默认方案开始开发：

- 四站并发保持不变。
- 默认使用平衡模式。
- ACG 游戏姬详情并发为 3，其余站点为 2。
- 请求间隔保持 0.2 至 0.5 秒。
- 图片改为全局后台队列，并发为 6。
- 启用 403、429、5xx、超时和验证页退避。
- SQLite 启用 WAL、busy timeout、写入锁与重试。
- 快速模式异常时自动回落至平衡模式。
- 完成后进行稳定、平衡、快速三轮真实测试，并根据结果微调各站参数。
